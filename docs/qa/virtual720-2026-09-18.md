## Implemented

- Explicit `--virtual-display-720p`, optional device-name selector and read-only
  `--display-probe`. Separate Start-Virtual720.ps1 / desktop shortcut.
- Detection uses adapter description/hardware identity AND attached GDI monitor
  name in the current session. A1920×1080 secondary screen, a file on disk,
  Microsoft Hyper-V Video or Microsoft RDP adapter is not assumed to be MttVDD.
- Exactly one matching virtual source is required unless selected by name.
  It must accept a supported1280×720 mode and pass physical-dimension readback.
- Encoder canvas remains720p even when a client requests1080p/native. Different
  monitor selections are rejected. Strict mode uses its chosen GDI source and
  does not enter the generic backend/RDP fallback chain.
- Captured GDI/DXGI source rectangles are checked before encode and monitor
  identity/dimensions are checked before RTP writes. Source mismatch/disappearance
  withholds frames or ends streaming instead of sending another monitor.
- Generic legacy discovery no longer installs drivers, restarts display services,
  enables wildcard devices, invents vendor-manager CLI arguments, or declares a
  driver created just because a config file exists. Explicit local API install
  requests now direct the operator to the reviewable provisioning script.
- Provisioning is separate, Administrator + confirmation gated. Official upstream
  release25.7.23 AMD64 archive (its filename says x86) is SHA256 pinned:
  e24210692b442b39af763536330ce78b423f19342b7a7792c26de3944e418b3a.
  Windows Authenticode catalog status must be Valid. No certificate import,
  signing/secure-boot bypass, service restart, tscon or automatic reboot.
- Fresh setup creates a root MttVDD device via documented SetupAPI, then asks
  Windows PnP to install the catalog-verified package. Config contains one720p
  resolution. Existing driver/config is preserved, not silently taken over.
  Failed installation attempts remove only a newly created device; staged files
  are retained and described for diagnosis/rollback.

## Critical unresolved deployment boundary

A virtual driver may attach to the console while an RDP session exposes only its
own display adapter. Installing a driver does NOT merge those sessions. The host
must run interactively in a session where the virtual monitor is actually visible.
This package does not move the host between sessions, disconnect RDP, unlock a
desktop, change primary topology, or move app windows. It refuses an invisible
source. Monitor index/topology changes may require restarting the XyDesk host.

No real driver installation, Device Manager readiness, actual virtual capture,
app placement, user RDP1280×720 acceptance or latency was exercised. Therefore
this is an implemented/tested integration candidate, NOT proof of an absolute
resolution lock on the user's runner. Driver policy/dependencies can still reject
loading; setup reports that rather than bypassing policy. Existing working audio
is untouched. Web/backend/APK and version remain unchanged in this session.

A16:9 source eliminates source-aspect padding; a non16:9 phone viewport still
needs space, cropping or stretching to fill all pixels. No no-bars-everywhere,
protected-screen, zero-lag or1080p60 claim.
