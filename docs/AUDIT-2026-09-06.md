## BAGIAN B — Diagnosis "stuck"

Diurut dari yang paling pasti (terverifikasi live di produksi) ke yang paling spekulatif.

### B.1 🔴 PASTI, produksi rusak sekarang: CSP masih domain lama

Bukti — header live `curl -I https://app.xydesk.my.id/`:

```
content-security-policy: default-src 'self'; script-src 'self';
  connect-src 'self' https://signal.xystudio.my.id wss://signal.xystudio.my.id
  https://news.xystudio.my.id; img-src 'self' data: https:; ...
```

Sumbernya: `web_deploy/static/_headers:6`. Berkas ini **terlewat** saat migrasi domain
6.5.4 (commit `909b423`, 49 berkas / 127 kemunculan).

Bukti pembanding — bundle live `assets/index-BKo6AgzB.js` sudah memanggil domain BARU:

```
1× https://signal.xydesk.my.id
1× https://news.xydesk.my.id
```

Dan domain lama sudah mati total: `curl https://app.xystudio.my.id/` → `http=000`, tidak resolve.

**Akibat:** browser memblokir `connect-src` ke signaling dan news. Client tamu di web tidak
bisa pairing (menggantung di "Menghubungi host…", lalu terkunci karena B.5), dan tab Berita
menampilkan "Beritanya belum bisa dimuat". Persis gejala "stuck".

Perbaikan: satu baris di `web_deploy/static/_headers` + dispatch Deploy Web.

### B.2 🔴 Sisa migrasi domain yang lain

| Berkas | Isi lama | Dampak |
|---|---|---|
| `web/public/robots.txt:4` | `Sitemap: https://app.xystudio.my.id/sitemap.xml` | SEO — sitemap 404, mesin pencari kehilangan peta |
| `news/seed.sql` (7×) | cover `https://app.xystudio.my.id/news/covers/*` | Re-seed = semua cover artikel mati. D1 live **sudah aman** (cover rilis-654/653 sudah `app.xydesk.my.id`) |
| `packaging/windows/XyDesk.iss:31` | `AppPublisherURL=https://app.xystudio.my.id` | Kosmetik, tapi muncul di dialog UAC/installer |
| `news/README.md:95` | pengirim email `news@mail.xystudio.my.id` | **Perlu dicek** — kalau domain pengirim Resend ikut dilepas, email langganan berita gagal kirim diam-diam |
| `SETUP.md:12` | "zona `xystudio.my.id`" | Dokumen menyesatkan operator berikutnya |

`CHANGELOG.md` / `HANDOFF.md` / `AGENT_BOARD.md` sengaja dibiarkan pakai nama lama — itu
**benar**, isinya catatan masa lalu, bukan konfigurasi berjalan.

### B.3 🟠 Tidak ada watchdog di web (lihat A.5)

Sudah dijelaskan. Ini bukan sekadar beda kosmetik — ini deadlock UI.

### B.4 🟠 `SignalingClient.isConnected` berbohong

`lib/webrtc/signaling_client.dart:97`:

```dart
bool get isConnected => _ch != null;
```

`_ch` diisi di baris 105, **segera setelah** `WebSocketChannel.connect(...)` — yang bersifat
lazy dan langsung返回. Artinya `isConnected` bernilai `true` bahkan sebelum handshake selesai,
dan tetap `true` kalau handshake gagal. Setiap UI yang membaca properti ini melaporkan status
yang salah.

Turunannya di baris 159:

```dart
void _send(SignalMessage m) => _ch?.sink.add(jsonEncode(m.toJson()));
```

Tidak ada `try/catch`. Kalau soket sudah error, `sink.add` melempar exception di dalam
callback → lolos ke `runZonedGuarded` di `main.dart:145` → hanya tercatat di DevLog, pengguna
tidak melihat apa-apa. Dan pesan yang dikirim sebelum soket benar-benar terbuka di-buffer;
kalau soket kemudian gagal, `sendPair` **hilang tanpa jejak** → menggantung sampai watchdog
20 detik.

### B.5 🟠 Layar hitam dengan status "connected"

Watchdog dibatalkan begitu fase pindah ke `connected` (`rtc_service.dart:258-262`), dan fase
itu dipicu oleh `RTCPeerConnectionStateConnected` (`rtc_service.dart:443-446`) — yaitu saat
transport ICE/DTLS jadi, **bukan saat frame video pertama tiba**.

Tidak ada pendeteksi "sudah connected N detik tapi `renderer.srcObject` masih null / tidak ada
frame". Repo ini pernah punya bug persis seperti ini (README: *"koneksi sukses tapi layar
kosong"*, dijaga test regresi di `host/tests/loopback.rs`) — tapi jaringnya hanya di sisi host.
Di sisi client, kalau track video tidak pernah sampai, pengguna menatap layar hitam yang
mengklaim tersambung. `SessionStats.resolutionLabel` sudah punya string jujur
(`'Belum ada gambar'`, `rtc_service.dart:159`) — tinggal dipakai sebagai pemicu, bukan cuma label.

### B.6 🟡 TURN diambil berurutan tanpa batas waktu per penyedia

`cloudflare/src/turn.js:199-226` — `collectIceServers` melakukan `await fetchProvider(...)`
di dalam `for` loop, **satu per satu**, dan tidak ada satu pun `AbortSignal.timeout` di
`fetchProvider`. Salah satu penyedia REST (`openrelayproject.metered.ca`, baris 102) yang
lambat akan menahan seluruh permintaan.

Client membatasi `/turn-ice` pada 5 detik (`rtc_service.dart:486`) dan — ini bagian yang
menyakitkan — **gagal secara diam-diam**:

```dart
if (res.statusCode != 200) return const [];
...
} catch (_) {
  return const [];
}
```

Jadi satu penyedia lambat → timeout 5 dtk → `[]` → sesi jalan dengan STUN saja → dua perangkat
di belakang NAT simetris/CGNAT **tidak akan pernah tersambung**, tanpa pesan apa pun. Ini
persis masalah yang ingin diselesaikan commit `ec06850` ("TURN multi-penyedia sebagai cadangan
berlapis"), tapi urutan sekuensial + tanpa timeout per penyedia + fallback bisu membuat
perlindungannya bocor di kasus yang paling mungkin terjadi.

Perbaikan: `Promise.allSettled` (paralel) + `AbortSignal.timeout(1500)` per penyedia +
catat di DevLog client saat TURN kosong (jangan bisu).

## BAGIAN C — Keputusan C++: **JANGAN ditambah.**

Ini dijawab dengan bukti, bukan selera.

### C.1 C sudah ada dan sudah jalan

`host/build.rs` mengompilasi **libopus 1.5.2 dari source C yang di-vendor**
(`host/vendor/opus/`: `src/`, `celt/`, `silk/`, `silk/float/`) memakai crate `cc`
(`host/Cargo.toml:78-79`), statis, hanya untuk target Windows. Alasannya tercatat rapi:
crate `opus` → `audiopus_sys` → CMake lawas yang ditolak runner Windows modern.

Artinya **toolchain C/C++ sudah aktif di CI dan sudah terbukti**. Kalau nanti memang butuh
C++, tidak ada pekerjaan persiapan yang tersisa.

### C.2 NVENC TIDAK butuh C++ — sudah selesai di Rust murni

ROADMAP dan README masih menyiratkan hardware encode sebagai pekerjaan yang belum ada
(README: *"hardware encode (NVENC/AMF/QSV) wajib untuk target itu"*). Kenyataannya di `main`:

| Berkas | Baris | Isi |
|---|---|---|
| `host/src/nvenc.rs` | 428 | NVENC SDK 12.2, dimuat **dinamis** (`LoadLibraryW` + `GetProcAddress`) |
| `host/src/nvenc_types.rs` | 2296 | binding FFI hasil generator, diverifikasi terhadap header C n12.2 (MIT, NVIDIA) |
| `host/src/nvenc_config.rs` | 353 | konstanta API, pemetaan status, perakit konfigurasi |
| `host/src/screen.rs:568` | — | `NvEnc::new(...)` dengan fallback otomatis ke openh264 |
| `host/src/screen.rs:109-110` | — | `nvenc_active()` → label encoder `"nvenc"` |

Pendekatan dinamis itu justru **alasan kenapa C++ tidak diperlukan**: mesin tanpa GPU NVIDIA
tetap jalan, dan program tidak crash saat startup bila DLL tidak ada. Menambahkan lapisan C++
di sini berarti menukar solusi yang sudah bekerja dengan masalah build baru, dan melanggar
aturan `host/` satu bahasa di CI (`docs/CI.md`).

Yang belum terbukti bukan **kode** NVENC — melainkan **angkanya di perangkat nyata**. Itu
butuh lab Windows dengan GPU, bukan butuh bahasa baru.

### C.3 Satu-satunya kebutuhan C++ yang nyata sudah diputuskan untuk TIDAK ditulis

Display virtual headless butuh driver **IddCx** — itu memang C/C++ kernel-mode. Tapi repo
sudah mengambil keputusan yang benar dan sudah mencatatnya:

- `packaging/windows/XyDesk.iss:16` → memakai **`ge9/IddSampleDriver` (MIT + CC0)** yang
  sudah jadi, disalin sebagai tugas installer opsional (`Tasks: vddinstall`, baris 107-123),
  dengan `skipifsourcedoesntexist` supaya installer tetap terbangun walau unduhan driver gagal.
- `host/README.md:208-215` → menulis driver sendiri butuh **sertifikat EV code-signing +
  INF + test signing**, yang **bertentangan dengan aturan ROADMAP "semua gratis, tanpa kartu
  kredit"**.
- `host/README.md:240-241` → *"Yang benar-benar butuh C/C++ bukan C#: vendor SDK (NVENC/AMF)
  atau kernel driver — dua-duanya di luar rencana."*

Vendor SDK sudah diselesaikan lewat FFI Rust (C.2). Kernel driver diselesaikan lewat memakai
karya orang lain yang berlisensi bebas (C.3). Keduanya keputusan yang sehat.

**Kesimpulan: menambahkan C++ sekarang adalah "poles sebelum bukti" — persis yang dilarang
ROADMAP aturan #1.** Yang layak dikerjakan bukan bahasa baru, melainkan mengukur angka yang
sampai hari ini belum pernah diukur.
